# Test Governance Core

本 Skill 是测试治理内核，不直接假设项目技术栈。用于先识别项目，再选择测试策略。

## 核心原则

- 先发现，再判断：从仓库文件、现有测试、文档、知识库和变更影响面推导测试方案。
- 用例可追踪：用户提供测试用例、验收清单或缺陷用例时，必须将用例映射到对应源码、接口/路由/CLI、配置、数据库/消息流、文档依据和已有测试，再据此确定覆盖范围、排除范围和缺口。
- 跨服务优先识别：默认假设真实业务测试可能跨多个服务或项目；先识别调用链、上游入口、下游依赖、数据流、认证/租户边界和各项目测试入口，再裁剪最小可验证范围。
- 真实环境强制优先：测试类 skill 默认必须使用用户指定或项目配置指向的真实环境、真实服务、真实账号和真实数据执行验证；缺少环境、账号、租户、服务地址、测试数据边界或写入授权等必要信息时，必须**暂停当前流程并主动向用户追问缺失项**（明确说出缺什么、为什么需要、用户应如何提供），**等用户补齐后立即恢复执行**；不能直接退出、不能只丢一份"待澄清清单"了事、不能用 mock、dry-run、离线模式、臆造数据、本地单元测试或模拟 e2e 替代真实验证。
- 非冒烟人工操作强制：除冒烟测试外，测试用例生成后的执行验证、集成、e2e、UAT、UI 功能、回归、bug 增量和端到端验证都必须模拟人工操作，覆盖真实浏览器、真实客户端、真实 CLI 或等价用户路径；接口调用、数据库查询和日志检查只能作为辅助证据，不得作为唯一验证方式。
- UTF-8 编码强制：所有测试输入、命令参数、脚本执行、终端输出、接口响应落盘、日志、截图说明、trace、报告和证据文件必须统一使用 UTF-8 编码；发现编码不确定或乱码时，必须先修正编码环境再继续执行或落盘。
- 真实环境阻断：只要真实环境数据不可用或必要信息缺失，测试用例生成、冒烟、集成、UI、回归、bug 增量和端到端验证都必须暂停；先记录已发现的源码/文档依据、缺失信息、风险，再向用户追问并等待补充；用户补齐前不得生成正式测试用例矩阵、不得运行测试、不得交付"测试通过"或"测试完成"结论；用户补齐后必须立即恢复执行。
- QA/QC 视角执行：以质量保障和质量控制视角设计与执行测试，关注可复现步骤、验收标准、缺陷证据、质量风险、放行建议和未覆盖范围，而不只做命令执行记录。
- 先复用，再补缺：优先运行项目已有测试命令，不强行引入新框架。
- 先最小闭环，再扩大覆盖：冒烟和 bug 增量测试只跑能证明风险的最小集合。
- 阻碍先澄清：遇到凭证缺失、外部服务不可达、真实数据写入风险、环境切换风险、destructive 操作、依赖权限不足或测试结论可能误导时，停止扩大测试范围，明确列出阻碍项、已掌握证据和需要用户补充的信息，**主动向用户追问下一步指示并等待回复**，用户回复后立即继续执行。
- 澄清后复用：用户已经澄清的环境、账号/租户、服务地址、真实测试数据、数据边界和授权信息必须记录到本轮上下文与测试报告中；澄清内容只落盘到被测项目的报告目录，默认写入 `test-governance/reports/clarifications.md` 或本次测试报告的“已澄清信息”小节，不写入用户级别目录或全局 skill 目录；除非出现新的阻断点、信息过期、环境切换、权限变化或数据写入风险变化，否则直接复用已澄清信息，不重复询问用户。
- 证据优先：所有结论必须绑定命令、日志、截图、接口响应、测试报告或明确跳过原因。
- 知识库可选：知识库检索增强上下文，但不可成为测试流程的单点阻塞。

## 标准流程

1. 唤醒记忆：使用 OpenViking 查询项目偏好、历史踩坑、测试经验。
2. 定位项目：读取根目录清单、README、docs、测试目录、包管理文件、CI 配置。
3. 识别项目边界：如果涉及多个仓库、多个服务、前后端协作、网关、消息队列、外部依赖或共享库，先画出服务/项目清单、调用关系、数据流和各自测试入口。
4. 识别技术栈：必要时运行 `references/stack-detection.md` 中的判定规则。
5. 检索知识：优先 OVA MCP；失败或超时时降级 OVA CLI；仍失败则只用代码和文档。
6. 用例映射：用户提供用例时，逐条映射到源码位置、接口/页面/CLI、配置、数据模型、文档依据和已有测试；没有证据的映射标记为待确认，不能写成事实。
7. 影响面分析：有代码改动、bug 或用户用例时，用可用的代码图谱、搜索或 diff 定位影响范围；跨服务场景要同时列出上游入口、下游依赖和需要联动验证的项目。
8. 确认真实环境：解析用户给出的租户、账号、服务地址、环境名、真实测试数据和数据边界；缺少关键信息或存在写数据风险时，先暂停所有测试流程，**主动向用户追问缺失项并等待补齐**，用户补齐后立即恢复执行并记录到被测项目 `test-governance/reports/` 复用，除非出现新的阻断点或风险变化。
9. 选择测试类型：仅在真实环境数据齐备后，按 `references/test-taxonomy.md` 分类为用例、冒烟、集成、UI、回归或增量测试。注意：
	   - 冒烟测试可选模拟或真实操作。
	   - 除冒烟测试外，其他执行型测试必须模拟人工操作，真实浏览器、真实客户端、真实 CLI 或等价用户路径至少覆盖一种；不得只做接口调用。
	   - 集成测试必须模拟人工操作并绑定真实服务、真实 API、真实数据库和受控数据；API 调用只能作为辅助断言。
	   - UI 测试是视觉比对（设计稿 vs 实际 UI），浏览器功能操作归入集成测试。
10. 执行或生成：仅在真实环境数据齐备后，以 QA/QC 视角执行或生成最小必要测试交付；如果真实环境不可测或必要信息缺失，**暂停执行并主动向用户追问缺失项、等用户补齐后立即继续**，不得直接输出阻断报告后退出，不得生成正式用例、不得运行测试、不得包装本地 mock/单测为真实测试结果。
11. 报告结果：按 `references/report-template.md` 输出证据化报告。报告必须包含：
	   - 耗时统计（各阶段起止时间与耗时）。
	   - 覆盖率统计与说明（接口、业务对象、权限、状态分支、源码文件等维度）。
	   - 通过率统计与说明（总用例数/通过/失败/阻塞/跳过及百分比）。
	   - 缺陷清单：缺陷类型归类（功能/性能/安全/兼容性/易用性/视觉/文档/其他）和缺陷修复建议（根因分析+修复建议）。

## 产物落盘位置

Skill 本体放在用户级 Codex skills 目录；某个项目产生的测试内容必须放回被测项目仓库。

默认使用仓库根目录下的长期维护目录：

```text
test-governance/
  manifest.yaml
  test-cases.md
  reports/
  evidence/
    screenshots/
    logs/
    traces/
```

规则：

- 测试用例矩阵默认写入 `test-governance/test-cases.md`。
- 冒烟、集成、UI、回归报告默认写入 `test-governance/reports/`。
- 用户澄清过的环境、账号/租户、服务地址、真实测试数据边界和授权信息默认记录到被测项目 `test-governance/reports/clarifications.md`，或写入同目录下本次测试报告的“已澄清信息”小节；不写入用户级别目录或全局 skill 目录。
- 截图、trace、命令日志等证据默认写入 `test-governance/evidence/`。
- 需要成为长期用户文档时，再同步到 `docs/TESTING.md`、`docs/TEST_CASES.md` 或项目既有文档入口。
- 一次性调试输出不要写入 README。
- 如果项目已存在 `.testing/`、`qa/`、`docs/testing/` 等测试治理目录，先沿用项目既有约定；新项目默认使用 `test-governance/`。

## 增量优先

每次执行测试类 skill 默认只做增量，不做全量重写。

- 测试用例：保留稳定 ID，只新增或更新受影响用例。
- 测试报告：每次执行新增一份运行报告，不覆盖历史报告。
- 证据文件：按日期、测试类型或 bug 编号追加，避免覆盖旧证据。
- 配置文件：只补缺失字段或更新明确相关字段。
- 只有用户明确说“全量更新”、“重建”、“刷新全部”、“重新整理所有测试资产”时，才允许全量重写目录内容。

## 知识库检索策略

默认顺序：

1. OVA MCP：`knowledge_search`、`knowledge_grep`、`resources_tree`。
2. OVA CLI：`ova knowledge search`、`ova knowledge grep`、`ova resources tree`。
3. 本地代码和文档：`rg`、GitNexus、Morph、README、docs、测试文件。

OVA 失败时不要终止任务。记录失败原因，例如超时、未登录、服务不可达，然后继续使用本地证据。

如果用户明确要求跳过 OVA 实际连通验证，仍保留上述策略作为默认接入规则，但报告中必须写清：

- OVA MCP / OVA CLI 是知识库检索的首选与后备通道。
- 本轮跳过的是外部连通验证，不是取消知识库接入策略。
- 不声明被跳过的租户、账号或远端链路已经验证通过。
- 质量评分只覆盖本轮实际执行范围；被用户明确跳过的外部验证不计入扣分项。

常用 OVA CLI 后备命令：

```powershell
$env:OVA_CLI_UPDATE_CHECK='0'
$server = $env:OVA_SERVER_URL
$profile = $env:OVA_PROFILE
$tenant = $env:OVA_TENANT_CODE
$username = $env:OVA_USERNAME
$password = $env:OVA_PASSWORD
pnpm --filter @openviking-admin/ova-cli run dev -- auth login --server $server --username $username --password $password --tenant-code $tenant --profile $profile --output json
pnpm --filter @openviking-admin/ova-cli run dev -- knowledge search --query "测试策略" --limit 5 --profile $profile --output json
pnpm --filter @openviking-admin/ova-cli run dev -- knowledge grep --pattern "冒烟测试" --profile $profile --output json
pnpm --filter @openviking-admin/ova-cli run dev -- resources tree --depth 2 --profile $profile --output json
```

## 何时读取 references

- 技术栈或命令不明确：读 `references/stack-detection.md`。
- 不确定测试类型边界：读 `references/test-taxonomy.md`。
- 需要 bug 增量范围：读 `references/bug-delta-rules.md`。
- 需要输出测试用例或验收记录：读 `references/report-template.md`。
- 需要选择 UI 工具：读 `references/ui-tooling.md`。
- 需要校准输出质量：读 `references/example-openviking-report.md`。

## 输出底线

每次测试治理任务至少说明：

- 上下文来源：代码、文档、知识库、历史记忆、bug 描述。
- 用户用例映射：列出用例与源码、接口/页面/CLI、配置、数据模型、文档依据和已有测试的对应关系；未确认项必须标记待确认。
- 跨服务/多项目范围：列出涉及项目、服务调用链、上游入口、下游依赖、数据流、认证/租户边界和各项目测试入口。
- 识别到的技术栈和测试框架。
- 使用的真实环境、账号/租户、服务地址、真实测试数据和数据边界；敏感信息必须脱敏。
- 已澄清信息：记录用户已提供并被本轮复用的环境、账号、数据和授权信息；无新阻断点时不得重复澄清；记录位置必须是被测项目 `test-governance/reports/`，不得写入用户级别目录。
- QA/QC 验收视角：质量目标、关键断言、缺陷判断、放行建议和未覆盖风险。
- 选择的测试范围与排除范围。
- 实际执行的命令或未执行原因。
- 非冒烟人工操作证据：除冒烟测试外，必须列出真实浏览器、真实客户端、真实 CLI 或等价用户路径的操作步骤、执行证据和断言结果；若仅有接口调用，必须标记为未满足验证要求。
- UTF-8 编码证据：说明本轮命令输入输出、报告和证据文件均按 UTF-8 处理；如发生编码问题，记录修正方式和剩余风险。
- 耗时统计：各阶段（环境准备、用例准备、测试执行、结果分析、报告生成）起止时间和耗时。
- 覆盖率统计与说明：至少从接口/路由、业务对象/数据模型、权限/租户边界、状态/流程分支、源码文件等维度评估覆盖情况。
- 通过率统计与说明：总用例数、通过数、失败数、阻塞数、跳过数和通过率百分比；失败/阻塞/跳过项必须说明原因。
- 缺陷清单：如有缺陷，按类型归类（功能/性能/安全/兼容性/易用性/视觉/文档/其他），并给出根因分析和修复建议。
- 真实环境阻断状态：缺少真实环境或必要信息时，必须在报告中明确"已暂停测试流程，正在等待用户补齐：<具体缺项>"，并列出只能作为参考的源码/文档证据；用户补齐前不得交付正式用例或测试结论。
- 遇到阻碍项时，列出阻碍项、证据、影响范围、需要用户补充的信息，**主动向用户追问下一步指示并等待回复**，用户回复后立即恢复执行。
- 结果证据和风险判断。

## 100 分优秀水准

当用户要求把测试类 skill 调试到“优秀水准”或“100 分”时，按以下维度自评，并把证据写入项目报告：

| 维度 | 达标标准 |
| --- | --- |
| 通用性 | 不绑定单一技术栈；先识别项目、服务边界和跨项目调用关系，再选择已有测试框架和命令。 |
| 用例追踪 | 用户提供用例时，能映射源码、接口/页面/CLI、配置、数据模型、文档依据和已有测试，并据此确定测试范围。 |
| 跨服务覆盖 | 跨服务或多项目场景明确上游入口、下游依赖、数据流、认证/租户边界、各项目测试入口和未验证依赖。 |
| 真实环境可信度 | 默认使用真实环境、真实账号、真实服务和真实数据边界验证；缺少必要信息时阻断所有测试流程并先澄清，不用 mock、dry-run、离线模式、本地单测或模拟 e2e 替代真实通过。 |
| 真实环境阻断 | 真实环境数据不可用时，用例生成、冒烟、集成、UI、回归、bug 增量和端到端验证全部暂停；主动向用户追问缺失项并等待补齐，用户补齐后立即恢复执行，不得只丢一份阻断报告后退出。 |
| QA/QC 质量视角 | 明确验收标准、关键断言、缺陷证据、质量风险、未覆盖范围和放行建议。 |
| 增量治理 | 测试用例、报告、证据和配置默认增量维护，保留稳定 ID 与历史报告。 |
| 自动化覆盖 | 至少覆盖冒烟、构建/类型、单测、集成或 e2e、UI 或等价用户路径；无法执行时给出明确原因。 |
| 非冒烟人工操作 | 除冒烟测试外，集成、e2e、UAT、UI 功能、回归和 bug 增量验证必须模拟人工操作，并提供真实浏览器、真实客户端、真实 CLI 或等价用户路径证据；只做接口调用不得判定通过。 |
| UTF-8 编码 | 所有测试输入输出、脚本、日志、报告和证据文件统一使用 UTF-8，编码异常必须先修正再继续。 |
| 阻碍处理 | 碰到外部依赖、凭证、权限、网络、数据写入风险或结论不确定时，停止扩大范围，给出证据并询问用户下一步指示。 |
| 澄清复用 | 用户澄清后的环境、账号、数据边界和授权信息会记录到被测项目 `test-governance/reports/` 并复用；除非出现新的阻断点、信息过期或风险变化，否则不重复澄清。 |
| 证据化报告 | 每个结论绑定命令、测试结果、截图/trace/日志或明确跳过原因。 |
| 知识库接入策略 | 明确 OVA MCP 优先、OVA CLI 后备、本地上下文兜底；跳过或失败时不得伪造通过结论。 |
| **耗时统计** | 报告包含各阶段（环境准备、用例准备、测试执行、结果分析、报告生成）起止时间和耗时。 |
| **覆盖率统计** | 报告从接口/路由、业务对象/数据模型、权限/租户边界、状态/流程分支、源码文件等维度评估覆盖率，并说明未覆盖原因。 |
